# Proposal: update-keeps-user-files

## 为什么

1. **程序目录里多一个文件，应用内更新就拒绝。** 解压版更新前要求安装目录与打包清单完全一致，用户在程序目录里建一个快捷方式（Windows 默认名 `DevKit.exe - 快捷方式.lnk`）就会得到「解压目录包含其他文件或已被修改…请将更新包另存并解压到新目录」。v0.3.2 → v0.3.3 实测连点 5 次都停在这句提示上，最后只能手工解压，和「重启并更新」的初衷相悖。
2. **发布包文件名带版本号。** `DevKit-0.3.3-win-x64.zip` 解压出来的目录也叫 `DevKit-0.3.3-win-x64`，每升一个版本就多一个目录（`DevKit-0.3.0-win-x64`、`DevKit-0.3.2-win-x64`、`DevKit-0.3.3-win-x64` 并存），快捷方式也得跟着改。

## 变更内容

- **用户文件原样保留。** 程序目录里不属于安装包的条目（快捷方式、用户的文件夹、放进程序子目录的文件）不再导致拒绝：它们随旧目录一起进备份，新版本确认启动后放回原处。旧安装缺了文件也照常更新，新版本把它补齐。
- **能在退出前发现的问题，就在退出前说。** Windows 下目录树里只要有任何文件或子目录被打开，整个目录就无法改名（哪怕是以允许删除共享的方式打开）。所以预检阶段逐个确认用户文件没有被占用（`ready=locked`）、没有与新版本自带的文件同名（`ready=collision`），有问题就列出来，应用不退出。占用只持续一瞬间的（杀毒、索引）自动重试，不算占用。
- **放不回的绝不删除。** 新版本启动后，放不回程序目录的用户文件留在 `.devkit-backup-<随机串>` 里，助手留下 `apply-leftover` 标记，工作台出现后提示一次位置（可一键打开该目录）。删除备份的前提是里面不再有任何非安装包的条目。
- **退出后才发现被占用时说明原因。** 替换失败会恢复旧版本并重新启动，同时写 `apply-detail=locked`，更新对话框从笼统的「上次更新未完成」变成指明是程序目录被占用。
- **发布包不带版本号。** `DevKit-win-x64.zip`、`DevKit-portable.exe`（`.sha256` 边车同名），应用内更新按新名称查找；发布说明里的下载表随之更新，清理旧行时新旧两种写法都认。

## 影响

- `resources/updater/DevKitUpdater.cs`（目录规则重写）、`src/main/services/updates/*`、`src/shared/app-updates.ts`。
- `package.json`（`artifactName`、`test:updater-harness`）、`.github/workflows/*`、`scripts/check-packaged-branding.cjs`、品牌测试与探针、`tests/probes/windows-updates.cjs`、README、AGENTS.md。
- 新增 `tests/probes/updater-harness.cjs`：用替身 DevKit.exe 驱动真实助手，不打包即可验证目录规则，CI 每次都跑。
- 便携版（单文件）的替换逻辑不变。

## 兼容性

- **v0.3.3 及更早的客户端按带版本号的名称找更新包**，之后的 Release 对它们会一直显示「新版本正在发布，请稍后检查」，需到发布页手动下载一次。截至 v0.3.3，带应用内更新的各版本在 GitHub 上的下载量合计二十余次，所以直接切换；若要兼顾它们，可在 CI 里同时上传一份带版本号的同内容包。
- **本修复随新版助手一起发布才生效。** 从 v0.3.3 及更早升到第一个含本修复的版本时，执行的仍是已安装版本里的旧助手，目录里有额外文件照样会被拒绝，需先把它们移出程序目录一次。
