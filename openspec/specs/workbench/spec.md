# Workbench

## Purpose

DevKit 的跨平台本地多工具工作台，统一管理工具面板、按需懒加载、平台能力裁剪、状态和持久化配置。它覆盖离线启动、会话隔离、用户设置恢复和本地数据保护，是其他工具共享的基础交互契约。

## Requirements

### Requirement: 跨平台离线工作台与平台能力解耦

应用 MUST 支持在 Windows、macOS 与 Linux 本地离线运行核心通信与调试工具（串口、SSH、本地终端、网络调试、TFTP、桥接、数据转换与文本对比、设备插件），无需云端账户或外网服务。依赖 Windows 原生 API 的工具（键鼠输入测试、键鼠宏、取色器）MUST 按 `process.platform === 'win32'` 在主进程与渲染进程工具注册表条件加载，并将 `koffi` 与 `uiohook-napi` 声明为 `optionalDependencies`。

#### Scenario: 非 Windows 平台启动

- **WHEN** 用户在 macOS 或 Linux 上启动 DevKit
- **THEN** 主进程跳过 Windows 专属原生服务加载，工具箱仅展示当前平台支持的核心工具，且不因缺失 Windows API 报错。

#### Scenario: 离线启动

- **WHEN** 设备没有互联网连接，用户启动 DevKit
- **THEN** 工作台及本地工具仍可打开和使用。

### Requirement: 多面板会话与按需懒加载

工作台 MUST 支持以标签承载独立工具面板，按工具声明允许多开或复用单例；渲染进程工具注册表 MUST 使用 `defineAsyncComponent` 对各工具面板按需拆包懒加载，避免首屏全量加载所有面板代码。分屏标签的各成员面板 MUST 同样遵循懒加载与按 panelId 的会话隔离。

#### Scenario: 并行调试

- **WHEN** 用户分别打开两个串口工具面板并切换标签
- **THEN** 两个面板的连接配置和状态彼此隔离，切换不会主动销毁会话。

#### Scenario: 分屏下双会话隔离

- **WHEN** 用户把 COM3 与 COM4 串口合并为一个分屏标签
- **THEN** 两成员的数据流、日志与连接状态按 panelId 完全隔离，互不串扰。

#### Scenario: 生产构建拆包

- **WHEN** 执行 `electron-vite build`
- **THEN** 各工具面板被拆分为独立的异步 JS/CSS chunk，仅在用户首次打开对应工具时加载。

### Requirement: 分屏标签并排工作

工作台 MUST 支持「分屏」：把任意两个非 home 标签合并为一个分屏标签——标签条上仅显示一个条目（标题合并为 "A | B"，仅一个关闭按钮），内容区左右并排同时渲染两个成员面板（非 CSS 隐藏）。合并与拆分 MUST 原地沿用成员面板：已建立的连接、终端已有的输出和面板内的输入状态保持不变，不因合并或拆分重新初始化。分屏标签 MUST 可整体拖拽排序；MUST 支持拆分回两个独立标签。单例工具并入分屏后 MUST 仍只此一份；被并入的会话若已在另一个分屏中，MUST 先移出原分屏再并入，同一面板不得同时属于两个分屏。工作台 MUST 仅支持两面板合并，不提供三面板以上或上下分屏。

#### Scenario: 两个串口合并并排

- **WHEN** 用户在 COM1 标签上右键选择「分屏」并在选择器中选中已打开的 COM2 标签
- **THEN** 标签条上 COM1 与 COM2 合并为一个条目（标题 "COM1 | COM2"、单个 X），内容区左右并排显示两个面板，各自的连接与数据流互不影响。

#### Scenario: 合并不中断会话

- **WHEN** 用户把一个已连接串口（终端里已有输出）的标签与另一个标签合并
- **THEN** 串口连接保持，终端里已有的输出继续保留，合并后新到的数据接在同一画面上；再把该分屏拆分回独立标签，连接与输出同样保持。

#### Scenario: 合并时新开工具

- **WHEN** 用户在某标签上发起「分屏」并在选择器中选择一个未打开的工具
- **THEN** 该工具的新实例作为第二个成员并入分屏标签并并排显示。

#### Scenario: 并入其他分屏中的会话

- **WHEN** 用户在分屏模式的选择器里选中一个正位于其他分屏中的会话
- **THEN** 该会话移入新的分屏，原分屏剩下的成员在原位置还原为独立标签，两者的连接均保持，同一面板不会同时出现在两个分屏里。

#### Scenario: 分屏中的单例工具

- **WHEN** 单例工具已是某个分屏的成员，用户再次从工具入口打开它
- **THEN** 工作台激活它所在的分屏条目，而不是新开第二份实例。

#### Scenario: 分屏内的高面板

- **WHEN** 内容高度超出分屏区域的工具面板（如编码转换）作为分屏成员显示
- **THEN** 用户可在该面板内滚动查看全部内容，另一成员不受影响。

#### Scenario: 终端分屏共用快捷命令栏

- **WHEN** 分屏的两个成员都是终端（串口 / SSH / 本地终端）
- **THEN** 两个终端自带的快捷命令栏都不显示，分屏左侧只保留一条共享命令栏：命令库仍是全局一份，栏顶标出当前发送目标；用户点进（或键盘聚焦）哪个终端，命令就发给哪个终端，该终端面板顶部亮主色标识线。共享栏可拖宽、可折叠，宽度与折叠状态记忆并在下次共享时恢复。

#### Scenario: 混合分屏各用各的命令栏

- **WHEN** 分屏成员中包含非终端工具（如串口与时间戳转换并排）
- **THEN** 不出现共享命令栏，终端成员照常显示自带的快捷命令栏。

#### Scenario: 关闭分屏标签

- **WHEN** 用户点击分屏标签的 X 或中键关闭
- **THEN** 两个成员面板一并关闭并释放资源，会话按身份记入最近会话。

#### Scenario: 关闭分屏的一侧

- **WHEN** 用户在分屏标签上右键选择「关闭左侧分屏」或「关闭右侧分屏」
- **THEN** 被关闭一侧的成员释放资源，另一侧原地还原为独立标签并保持连接；若该分屏正在显示，接着显示留下的一侧。

#### Scenario: 拆分回独立标签

- **WHEN** 用户在分屏标签上右键选择「拆分为独立标签」（或按 `Ctrl+Shift+\`）
- **THEN** 成员还原为两个独立标签，面板状态与连接保持，焦点落在第一个成员。

#### Scenario: home 保护

- **WHEN** 用户尝试合并「工具箱」home 标签
- **THEN** 操作被拒绝，home 恒保持在首位。

### Requirement: 分屏宽度调整与持久化

分屏标签 MUST 在两个成员面板之间提供贯通内容区全高的分隔条，并带有常驻可见的拖拽把手；支持拖拽调整两成员宽度，左成员占扣除分隔条后可用宽度的 20%–80%。没有记忆值或记忆值无效时，两成员 MUST 默认均分。分隔宽度 MUST 持久化并在重启后首次合并分屏时恢复；分隔条错位版本写出的记忆值 MUST 丢弃。拖拽被打断（切换窗口、指针被系统取消）后 MUST 结束拖拽，之后的悬停移动不得继续改变宽度。合并分屏 MUST 提供键盘操作（`Ctrl+\` 对当前标签发起合并、`Ctrl+Shift+\` 拆分当前分屏标签）。

#### Scenario: 首次分屏默认均分

- **WHEN** 没有有效记忆值的用户合并两个标签（首次使用，或此前只留下过分隔条错位版本写出的值）
- **THEN** 两成员宽度相等，分隔条位于内容区垂直中线并贯通全高；鼠标在两面板交界处任意高度按下拖动都能调整宽度。

#### Scenario: 拖拽调宽后重启

- **WHEN** 用户拖动分隔条将左成员调至约 60% 宽并重启应用
- **THEN** 下次合并分屏时恢复上次的分隔宽度。

#### Scenario: 拖拽被打断

- **WHEN** 用户拖动分隔条的过程中切换窗口，或指针被系统取消
- **THEN** 分隔条停在当前位置并结束拖拽，之后仅移动鼠标不再改变两成员宽度。

#### Scenario: 快捷键发起与拆分

- **WHEN** 用户在普通标签上按 `Ctrl+\` 后在选择器选中目标
- **THEN** 两标签合并为一个分屏标签；再按 `Ctrl+Shift+\` 拆分回独立标签且顺序保持。

### Requirement: 配置持久化

工作台 MUST 将用户设置和会话信息存于本机，并在重新启动后恢复适用设置。

#### Scenario: 重新启动

- **WHEN** 用户修改终端字体或会话选项并重新启动
- **THEN** 原有设置从本地配置加载。

### Requirement: 安全边界

工具的网络访问和系统权限 MUST 仅由对应功能请求，应用 MUST 不自动上传宏、设备日志或用户配置。

#### Scenario: 记录敏感操作

- **WHEN** 用户录制本地输入宏或串口日志
- **THEN** 本地数据不会被自动发送至外部服务。

### Requirement: 多平台分发构建

发布构建 MUST 为 Windows（便携版/ZIP）、macOS（DMG/ZIP）与 Linux（AppImage/tar.gz）提供对应 `electron-builder` 构建配置。

#### Scenario: 首次运行

- **WHEN** 用户启动便携版或打包产物
- **THEN** 工具可不依赖云端环境本地运行。

### Requirement: 工作台导航与内置模块目录

工作台 MUST 将工具标签和全局扩展、换肤入口布置于标题栏，工具箱 MUST 按工具用途分组并支持名称和描述筛选。

#### Scenario: 找到并打开工具

- **WHEN** 用户在工具箱搜索一个已支持的工具
- **THEN** 匹配项可通过点击或键盘激活，工作台使用该工具既有的标签实例策略。

#### Scenario: 宽屏工具箱布局

- **WHEN** 用户在宽屏（≥1440px）打开工具箱
- **THEN** 分类按竖向顺序逐组堆叠，全部分类共用同一个栅格：同类、跨类工具卡片等宽等高（描述固定占两行高度），分类标题横跨整行作为分隔，两侧不出现大片空白。

#### Scenario: 工具分类的粒度

- **WHEN** 用户浏览工具箱
- **THEN** 工具按「串口与设备调试 / 终端与网络 / 数据转换与计算 / 文本、屏幕与自动化」四类归组，每组 3–4 个工具，不出现某类塞十余个、另一类只有两三个的失衡分组。

#### Scenario: 窄窗口工具箱布局

- **WHEN** 窗口窄于 560px 时打开工具箱
- **THEN** 工具卡片改为单列排列，描述文本被截断为最多两行，卡片不横向溢出。

### Requirement: 工作台与终端工作区的版面间距

标题栏及其下方的终端工作区各栏 MUST 保持统一、可读的间距：标签不贴窗口边缘，栏内按钮不相互挤压，串口终端与 SSH 终端 MUST 使用同一套间距。

#### Scenario: 打开终端工作区

- **WHEN** 用户在 100% 缩放的窗口中打开串口终端或 SSH 终端
- **THEN** 标题栏高度不小于 44px，连接栏、操作栏、发送栏的垂直内边距不小于 7px、左右内边距不小于 12px，相邻控件间距不小于 6px；标签栏、侧栏、操作栏与状态栏的视觉密度一致。

#### Scenario: 串口与 SSH 的栏位一致

- **WHEN** 用户在串口终端与 SSH 终端之间切换
- **THEN** 连接栏、侧栏、操作栏与终端内边距一致，不出现一侧明显更紧或更松的跳变。

#### Scenario: 浏览内置模块

- **WHEN** 用户从标题栏打开扩展中心并选择一个可用内置模块
- **THEN** 详情提供打开工具标签的入口，重复打开扩展中心不会创建重复标签。

#### Scenario: 快速打开工具

- **WHEN** 用户点击标签栏的加号或按 Ctrl+K
- **THEN** 当前标签仍在背景，工具搜索面板支持方向键选择、Enter 打开及 Esc 关闭。

#### Scenario: 关闭串口标签后继续调试

- **WHEN** 用户关闭有连接参数的串口标签，然后从工具箱的最近会话重新打开
- **THEN** 新标签保留该串口的连接参数，用户主动点击连接后才打开串口。

#### Scenario: 标题栏换肤

- **WHEN** 用户打开外观浮层
- **THEN** 全部内置配色以色板栅格一次性列出（无需展开「更多」），可选择配色、按名称筛选或开关「跟随系统」；选择后界面与终端即时更新，浮层关闭后工作区继续可用。

### Requirement: 统一应用标识

工作台 MUST 使用用户最终附件中的 DK Monogram 作为统一应用标识：左侧 D 与右侧 K 连为一体，D 内部保留清晰的 D 形负空间，字母图形由蓝色向紫色渐变。标题栏 MUST 使用无底板的 DK 标识；应用图标 MUST 将同一字母图形置于深紫色圆角方形底板上。各尺寸资源 MUST 从同一可编辑 SVG 母版派生。

#### Scenario: 深浅主题标题栏与版本入口

- **WHEN** 用户在深色或浅色主题下打开工作台，并点击标题栏的 DevKit 标识入口
- **THEN** 标题栏清晰显示蓝紫渐变 DK 连体标识与 DevKit 名称，D 形负空间保持可辨认，原版本信息浮层仍可打开并展示应用及运行时版本，标题栏的导航和窗口控制保持可用。

#### Scenario: Windows 打包与运行时图标一致

- **WHEN** 用户查看本次 Windows 打包的 DevKit 可执行文件并启动应用
- **THEN** 可执行文件图标与运行时任务栏图标均使用深紫圆角底板上的蓝紫 DK 连体设计；Windows 原生窗口使用随包提供的多尺寸 ICO，其他平台沿用对应 PNG，Windows 应用身份保持为 `com.embedded.devkit`，任务栏重启入口指向 DevKit 自身。打包验证须核验目录版、便携启动器与 ZIP 内应用的图标资源，以及 ASAR 内运行时 PNG/ICO 与本次生成资源一致；Windows 原生窗口的图标和应用身份须单独验证。

#### Scenario: 插件登录窗口的应用标识

- **WHEN** 插件需要用户通过普通登录子窗口完成认证
- **THEN** 子窗口在显示前使用与主窗口相同的原生应用图标和 Windows 应用身份，登录页面地址不成为任务栏重启入口；原有认证页面、安全边界和取消行为保持不变。

#### Scenario: 辅助窗口与功能图标

- **WHEN** 用户打开宏状态条、全屏取色器或浏览工具列表
- **THEN** 辅助窗口保留既有的跳过任务栏行为，各工具保留表达其功能的图标，不因应用品牌统一而新增托盘或任务栏入口。

#### Scenario: 已发布包与已有固定项

- **WHEN** 品牌修复合入主分支，但用户仍使用旧下载包或已有任务栏固定项
- **THEN** 应用不宣称旧 Release 附件已随合并更新，也不静默改写用户已有的固定快捷方式；排查说明先核对实际构建、启动路径和固定目标，再检查 Shell 图标缓存。

#### Scenario: 单源派生小尺寸资源

- **WHEN** 维护者从确认后的 DK SVG 母版重新生成应用图标资源
- **THEN** 界面标识、单色备用标识、应用 PNG 和多尺寸 Windows ICO 保持相同的 DK 连体轮廓与 D 形负空间；ICO 包含 16、20、24、32 像素等小尺寸档位，缩小时仍能辨认字母组合，生成结果可检查是否与母版一致。

### Requirement: GitHub 应用版本更新

Windows x64 发布版 MUST 支持从官方 GitHub Release 检查同一分发格式的稳定更新、查看发布说明、按需下载和重启更新。更新过程 MUST 保留应用用户数据。解压版在原目录更新时 MUST 保留程序目录中不属于安装包的文件和目录（如用户创建的快捷方式、资料文件夹），更新后放回原处；无法放回的 MUST 原样留在备份目录并告知用户其位置，不得删除。程序目录里的文件正被其他程序占用、或与新版本自带的文件同名而无法原路径更新时，应用 MUST 在退出前列出涉及的文件并给出处理办法，当前程序与文件保持不变。发布包的文件名 MUST 不带版本号（`DevKit-win-x64.zip`、`DevKit-portable.exe`），应用内更新按该名称查找对应格式的发布包。GitHub API 匿名配额受限（403/429）时，应用 MUST 回退到零配额的发布页通道解析最新稳定版本（版本号取自跳转后的最新发布页，包大小取发布直链，SHA-256 取随包上传的 `<包名>.sha256` 边车附件）；三者齐全时 MUST 支持与常规路径相同的应用内校验下载与重启更新，不齐全时 MUST 提示无法在应用内更新并保留发布页入口。CI 发布 Windows 包时 MUST 同时上传各包的 `.sha256` 边车文件。更新包下载 MUST 先测官方直连：速度足够时只从官方下载，不联系任何第三方；不足时 MUST 改用实测明显更快的加速镜像，并在界面上标出所用镜像。无论来自哪个来源，下载结果 MUST 通过大小与官方 SHA-256 校验，不通过 MUST 换下一个来源重试；传输中断或长时间没有数据时 MUST 从已下载的位置续传。镜像列表 MUST 可经配置 `updates.mirrors` 替换。下载期间标题栏的更新入口与状态栏 MUST 显示百分比与速度；更新对话框 MUST 提供「后台下载」，关闭对话框后下载继续。

#### Scenario: 自动发现新版本

- **WHEN** 后台检查发现比当前版本新的稳定 Release，且对应的 Windows 发布包已上传并可验证
- **THEN** 工作台提示有新版本，可查看当前版本、新版本和发布说明，并可选择下载或稍后处理。

#### Scenario: API 限流时发布页回退下载

- **WHEN** 用户检查更新时 `api.github.com` 返回 403/429，而最新发布带 `.sha256` 边车
- **THEN** 版本号、包大小与校验和经发布页通道获取，应用内下载、校验与重启更新照常完成，全程无需 API 配额。

#### Scenario: 限流且发布无校验文件

- **WHEN** API 受限且目标版本的发布没有 `.sha256` 附件（v0.3.0 及更早）
- **THEN** 提示无法在应用内直接更新并可打开发布页手动下载；API 配额恢复后应用内更新恢复可用。

#### Scenario: 离线或发布包尚未上传

- **WHEN** 应用离线、GitHub 请求失败或发布包尚未上传完成
- **THEN** 工作台仍可操作。手工检查显示相应结果，后续仍可再次检查。

#### Scenario: 下载和延后重启

- **WHEN** 用户点击下载且完整性校验通过
- **THEN** 应用显示进度和下载完成状态，提供「重启并更新」与「稍后」。关闭并重新打开工作台后仍可使用已验证的待更新包。

#### Scenario: 官方直连够快时不经过第三方

- **WHEN** 用户开始下载，官方直连的实测速度足够
- **THEN** 更新包只从 GitHub 官方地址下载，应用不联系任何镜像，界面不出现镜像标注。

#### Scenario: 官方直连慢时经镜像加速

- **WHEN** 用户开始下载，官方直连的实测速度不足，而有加速镜像明显更快
- **THEN** 应用从最快的镜像下载，对话框标出所用镜像；直连与镜像都不理想时仍回到官方直连完成下载。

#### Scenario: 下载中断后续传

- **WHEN** 下载过程中连接中断、被重置或长时间没有数据
- **THEN** 应用从已下载的位置续传而不从头开始；多次续传仍不完整时换下一个来源重试。

#### Scenario: 下载进度常驻可见

- **WHEN** 更新包正在下载，用户在更新对话框里点「后台下载」
- **THEN** 对话框关闭、下载继续；标题栏右上角的更新入口显示下载百分比，状态栏显示百分比、速度与所用来源，下载完成后入口变为「重启更新」。

#### Scenario: 重启应用更新

- **WHEN** 用户选择重启并更新且原路径满足更新条件
- **THEN** 应用正常结束现有会话，再以同一启动路径打开新版本，保留用户配置、插件和日志，以及程序目录里用户自己放入的文件（如快捷方式、资料文件夹），内容不变。

#### Scenario: 安装条件不足

- **WHEN** 应用所在目录无法安全替换（含符号链接、缺少核心文件或安装清单）或没有写权限
- **THEN** 应用在退出前显示原因并允许另存校验成功的更新包，保留当前程序和用户文件。

#### Scenario: 程序目录里的文件正被占用

- **WHEN** 用户选择重启并更新，而程序目录里有文件正被其他程序打开
- **THEN** 应用不退出，列出被占用的文件并建议关闭相关程序后重试或另存更新包；占用解除后再次重启即可完成更新。

#### Scenario: 用户文件与新版本同名

- **WHEN** 用户选择重启并更新，而程序目录里的用户文件与新版本自带的文件同名
- **THEN** 应用不退出，列出同名的文件并建议先移出程序目录或另存更新包；移走后再次重启即可完成更新。

#### Scenario: 更新后没能放回的文件

- **WHEN** 更新完成后有个别用户文件无法放回程序目录
- **THEN** 新版本照常启动并可用，这些文件原样留在程序目录旁的备份目录里，应用提示一次该位置，且不删除该备份目录。

#### Scenario: 退出后才发现目录被占用

- **WHEN** 应用已退出后才发现程序目录被其他程序占用，替换无法完成
- **THEN** 原版本原样恢复并重新启动，程序目录里的用户文件保持不变；更新对话框说明上次未完成的原因是程序目录被占用，可重试或另存更新包。

#### Scenario: 发布包文件名

- **WHEN** CI 发布 Windows 包
- **THEN** 附件为 `DevKit-win-x64.zip` 与 `DevKit-portable.exe` 及各自的 `.sha256`，文件名不含版本号；用户解压 ZIP 得到的目录名不随版本变化，应用内更新按该名称找到对应格式的包。

#### Scenario: 损坏的更新包

- **WHEN** 某个来源给出的数据与发布附件公布的长度或 SHA-256 不一致
- **THEN** 该来源的数据被放弃并换下一个来源重试；所有来源都不一致时应用报告失败并允许重新下载，原程序可以继续使用。

#### Scenario: 替换镜像列表

- **WHEN** 用户在 `config.json` 的 `updates.mirrors` 中配置了镜像前缀
- **THEN** 下次下载用该列表替换内置镜像；非法前缀被忽略，列表为空时仍用内置镜像。

### Requirement: 工具标签可移至独立窗口

工作台 MUST 支持将任意非首页标签（包括合并分屏标签）拖离主窗口标签栏或通过右键菜单「移至新窗口」移到独立窗口。独立窗口 MUST 只承载该标签，无首页；迁移 MUST 保留面板实例、输入、连接及终端输出。工作台 MUST 支持在主窗口内拖拽排序、取消拖拽，以及将独立窗口的标签移回主窗口。

#### Scenario: 拖离标签栏

- **WHEN** 用户将工具标签拖离标签栏并在栏外释放鼠标
- **THEN** 标签随拖动出现在独立窗口，释放后从主窗口标签栏中移除；若移出的是当前标签，主窗口显示相邻标签或首页。

#### Scenario: 在栏内拖拽或取消拖拽

- **WHEN** 用户在标签栏内拖拽排序，或拖离后在主窗口的标签栏内释放，或按 Esc 取消
- **THEN** 栏内释放只调整标签顺序，取消拖拽保持原位置，首页始终固定在首位。

#### Scenario: 从菜单移出正在使用的标签

- **WHEN** 用户在工具标签上选择「移至新窗口」
- **THEN** 独立窗口只显示该标签内容，原有工具状态和连接继续使用；合并分屏的两个成员整体移入，布局和连接保持。

#### Scenario: 移回主窗口

- **WHEN** 用户将独立窗口内的标签拖回主窗口标签栏，或点击「移回主窗口」
- **THEN** 标签回到主窗口并激活，独立窗口关闭，面板和会话保持。

#### Scenario: 保留分屏比例

- **WHEN** 用户在独立窗口里调整分屏分隔条，再将该标签移回主窗口
- **THEN** 同一分屏按调整后的比例显示。

#### Scenario: 在独立窗口关闭弹层

- **WHEN** 用户点击下拉框或弹出菜单外部，或在独立窗口的设置弹窗中按 Esc
- **THEN** 当前弹层按工具的常规关闭规则收起，主窗口里的弹层不受影响。

#### Scenario: 独立窗口生命周期

- **WHEN** 用户关闭主窗口，随后继续操作独立窗口，或关闭独立窗口
- **THEN** 独立窗口可继续使用；关闭独立窗口释放其面板资源，聚焦其他窗口无需重开工具。

#### Scenario: 首页固定

- **WHEN** 用户尝试将首页拖出，或打开首页的右键菜单
- **THEN** 首页保持在主窗口，菜单没有「移至新窗口」。

### Requirement: 应用语言实时切换与持久化

工作台 MUST 在设置中提供 `简体中文（zh-CN）` 与 `English（en）` 两种应用语言，MUST 在没有有效偏好时默认使用中文，并 MUST 持久化用户选择。切换语言 MUST 就地更新已显示的 DevKit 自有界面，不得刷新工作台、重建工具面板、改变 `panelId`，也不得中断已有连接、传输、终端缓冲或未提交输入。

#### Scenario: 首次启动默认中文

- **WHEN** 用户首次启动应用，或已保存的语言偏好缺失或无效
- **THEN** 工作台从首次可交互画面起使用简体中文，且全部工具仍可正常打开。

#### Scenario: 实时切换为英文

- **WHEN** 用户在设置中把语言从简体中文切换为 English
- **THEN** 当前工作台、已打开的内置工具及可更新的 DevKit 自有窗口就地显示英文；之后打开的 DevKit 原生文案使用英文，无需重载或重启应用。

#### Scenario: 切换语言不打断会话

- **WHEN** 用户在串口、SSH、本地终端、网络或传输会话运行期间切换语言
- **THEN** 连接与任务继续运行，终端缓冲、面板输入、标签顺序和 `panelId` 保持不变，只有应用自有展示文案改变。

#### Scenario: 重启恢复语言偏好

- **WHEN** 用户选择 English 后正常退出并重新启动 DevKit
- **THEN** 首次可交互画面直接使用英文；再次选择简体中文并重启时同样恢复中文。

### Requirement: DevKit 自有文案完整本地化与数据边界

DevKit MUST 为应用壳、设置、全部内置工具及应用创建的原生窗口、菜单、对话框、通知和错误说明提供完整的 `zh-CN` 与 `en` 文案。两种语言目录 MUST 使用一致的消息键并支持动态参数。应用 MUST 将终端输出、设备/网络/传输数据、文件和日志载荷、用户输入、插件内容、第三方页面及外部程序输出保持原样，不得为了界面本地化而翻译或改写这些数据。

#### Scenario: 浏览全部内置工具

- **WHEN** 用户选择任一支持语言并依次打开工具箱中的全部 DevKit 内置工具及其设置、确认、空态和错误状态
- **THEN** 工具名称、说明、控件、状态与应用自有提示均使用所选语言，不正常暴露内部消息键或混入另一语言的应用自有文案。

#### Scenario: 打开应用自有原生界面

- **WHEN** 用户在所选语言下触发 DevKit 创建的辅助窗口、认证窗口、更新窗口、原生菜单、对话框、通知或错误说明
- **THEN** 其中由 DevKit 提供的文案使用所选语言；操作系统通用控件和第三方页面不被宣称为 DevKit 翻译范围。

#### Scenario: 设备和远端数据保持原样

- **WHEN** 当前语言为 English，而终端、串口、设备、网络、文件、日志、插件或第三方页面包含中文或任意原始字节内容
- **THEN** DevKit 按原有编码和展示规则传递该内容，不翻译、不替换，也不因 locale 改变协议数据。

#### Scenario: 本地化资源不完整

- **WHEN** 运行时无法解析某个应用自有消息键或已保存 locale 无效
- **THEN** 应用安全回退中文并保留可诊断信息，工具操作和现有会话继续可用；目录一致性测试在发布前报告缺失或空白译文。

### Requirement: 双语 README 与 Release 内容兼容

仓库 MUST 提供内容完整的中文 `README.md` 与英文 `README.en.md`，并在两者的显眼位置互相链接。同一 GitHub Release 的说明 MUST 同时包含中文与 English 章节，MUST 只包含一张供两种语言共用的双语下载表，并 MUST 精确保留 `## 下载` 标题和稳定附件名以兼容已部署的更新读取器。发布 CI MUST 只更新唯一 marker 对限定的下载表区段；应用内更新界面 MUST 同时展示该 Release 的中文与 English 章节。

#### Scenario: 从任一 README 切换语言

- **WHEN** 用户打开 `README.md` 或 `README.en.md`
- **THEN** 当前文档可独立提供完整的安装、使用、开发与发布信息，并在顶部通过明确链接打开另一语言版本。

#### Scenario: 查看双语 Release

- **WHEN** 维护者发布一个包含本次约定的 GitHub Release
- **THEN** 同一发布说明包含中文与 English 章节，之后只有一个精确名为 `## 下载` 的下载段和一张双语表，表中继续使用 `DevKit-portable.exe` 与 `DevKit-win-x64.zip`。

#### Scenario: CI 刷新下载表

- **WHEN** 发布流水线在 Release 附件生成后刷新下载信息，且说明中存在唯一、顺序正确的下载表 marker 对
- **THEN** 只有 marker 内的双语下载表被替换，marker 外的中文、English 与人工维护内容逐字保留。

#### Scenario: Release marker 无效

- **WHEN** Release 说明中的下载表 marker 缺失、重复或顺序错误
- **THEN** 发布流水线明确失败且不重写整篇说明，维护者可修复模板后重试。

#### Scenario: 应用内查看发布说明

- **WHEN** 应用发现符合条件的新版本并显示该 Release 的发布说明
- **THEN** 更新界面同时展示中文与 English 两个章节，不因当前应用语言隐藏或删除其中一个章节，并继续识别唯一的 `## 下载` 段。
